## 3. Benchmarks

`tools/bench-ab.mjs` (`docs/notes/player.md`, "Measuring two builds"): two builds, one server
each, one e2e Firefox, ABBA order per round, one warm-up round thrown away. `--rate`/`--ttfb` put
the media on one shared slow line (first in, first out, 64 KiB at a time). A verdict needs the
medians apart by more than twice the larger spread (MAD) and the measure's floor, and a rank-sum
test with p < 0.05; otherwise "same". It measures; it never fails on a number.

### Several tabs (the owner's question)

`--scenarios tabs`: three players paused in background tabs, one playing in front, each video
(90 s, 2.1 Mbit/s HLS) on a loopback host of its own, all on one line.

| Line, rounds | Measure | main | branch | |
|---|---|---:|---:|---|
| 8 Mbit/s, 7 | the player in front has its whole video | 66.1 s | 29.6 s | better, 7 of 7 |
| | all four have theirs | 109.1 s | 92.3 s | better, 7 of 7 |
| | first frame in front, from its first request | 1168 ms | 1076 ms | better, 7 of 7 |
| | seconds ahead in front, 10 s in | 18.8 s | 19.1 s | same |
| 40 Mbit/s, 5 | in front; all four | 6.5 s; 18.3 s | 6.5 s; 18.2 s | same |

Controls (8 Mbit/s, 3 rounds): main against the branch before the turns (2f8cd482): 64.0 and
63.6 s in front, 109.9 and 110.0 s for all: the same, so the difference is the turns. Main
against a copy of itself: the same in every measure.

**A caveat that cost an evening.** The tabs scenario's "player modules ready" (a new tab's page
start) comes in two speeds, about 0.25 s and 0.6 s, by the Firefox session, not by the build:
main had 0.25 s in every round of one run and 0.6 s in every round of the next. Counted from
the navigation, the first frame read 0.27 s *worse* for the branch, 7 of 7 rounds, p < 0.001 -
an artifact. The first frame is now counted from the page's first request for the video, and
that measure's floor is 0.5 s, so the report gives it no verdict below that. The reports in
`docs/bench/2026-11-14/` of the tabs runs were written before the floor was raised: their
"player modules ready: worse" line is this artifact. What causes the two speeds was not found.

## 4. Known and open

Security

- Code scanning: no open alert on main or on the PR. Two results in `UrlMatchList.test.mjs`
  (`js/regex/missing-regexp-anchor`) are dismissed as false positives, as ten of the same were on
  main: the test's hostnames go through a function whose `~` branch alone makes a regex.
- Dependabot #80, `deepmerge` (prototype poisoning, GHSA-gcqx-w48m-w2h4): dev-only (web-ext's
  linter), no fixed release exists (4.3.1 is affected and the latest). Waits for upstream.
- Not fixed, the owner's decision: PE-7, a crafted MP4 that claims billions of samples makes
  mp4box allocate one object per sample on the add-ons' shared process (4 million samples, 2.2
  GB, measured). Recommended: a per-file sample budget, beyond it Firefox plays the file itself.
- Built on 2026-11-15 (SEC-3): `patched-libraries.yml` installs a new npm release only in a job
  with a read-only token; a second job, which installs nothing, checks what the first hands on and
  pushes (`docs/notes/workflows.md`, "Patched libraries: two jobs").
- Hardening recommended, not built (report section 8): a tag ruleset; the mpv helper starts any
  `mpv*.exe` path and passes `fs-*` tags unchecked; the fail-safe attaches AMO's signed file without
  comparing it with the built zip; `fsaunpack` answers `Access-Control-Allow-Origin: *`; the
  signing job also runs the tests.
- The content scripts, reviewed on 2026-11-15 (what a page can feed them). Built (#686):
  - One reading of a page's `<track>` files takes at most 64 tracks and 64 MB, shared by its
    requests. A track that fails gives its bytes back to the others.
  - A frame keeps at most 64M characters of track text; the oldest go first, the tracks just
    read last. Before this, a page that named new track files at each stream had all of them
    kept.
  - `episode-links.js` `normalize` is linear. Its regex took 11.7 s on 200k dashes, and it
    runs on every same-site link at each playlist poll.
  - Not built: reading the tracks only while FastStream is on. Reading them while off is
    deliberate (`backgroundDetection.test.mjs`, "asks a page that is off for its captions").
- Checked, nothing to fix:
  - A page's quality list reaches the player and mpv only when it holds the file the browser
    itself requested, and only its entries on that file's host count (`listForSource`).
  - The page transport fetches in the frame the stream was detected in (`pageFrameId`), with
    the cookies that frame's own request had. The player's page frame stands in only for a URL
    the user typed.
  - `fs-*` tags a page puts in a stream URL's fragment are dropped before FastStream's own are
    added (`withoutFsTags`).
  - Subtitle text is drawn by vtt.js's `parseContent`: an allowlist of tags, and text nodes.
- Recommended, not built (behaviour, the owner's decision):
  - After the event page restarted, the sources are recovered from the page's Resource
    Timing entries and its videos' `currentSrc` (`recoverFrameSources`). A page can name a
    local-network address there, which the background's length read and mpv then request: blind
    GETs outside Firefox's own checks. A filter that allows private addresses only for a page on
    one would close it, and could stop a local media server shown on a public page.
  - `UrlMatchList`: a regex the user types runs on every address. A catastrophic one (or one in
    an imported options file) slows every page.

Checked on 2026-11-15 (they were unverified)

- C-1's premise holds in Firefox 160.
  - For a MediaSource with its duration set first (FastStream's order), a start time set at
    `readyState` 0 is kept, and `seeking` fires after `loadedmetadata`, twice.
  - Without a duration, the start is dropped silently.
  - A plain file keeps it.
- C-4: a write past the space there is fails cleanly. `writeAll` throws on a short write
  (`opfs-worker.mjs`), and the fragment stays in RAM (`FSBlob.saveBlobInOPFSAsync`). Several
  players planning with the same free space cost RAM or a download again, never a broken
  fragment. Not built.
- R-4 was real: a second player in the tab became the main player and autoplayed. Fixed in
  #684: the `PING` that wakes the event page counts the player, once the kept tab state is
  back.
- A reload whose page takes over 3 s keeps the buffer. Measured with
  `reload-keeps-buffer.e2e.mjs` ("…takes longer than 3 s to come", the page answered 5 s
  late), passing on main:
  - 4 s into the reload the old page is still there, and its player, gone at `beforeunload`,
    has loaded again (`StayedMs`). It has no stream then: it takes nothing back from the stash,
    and asks the old link for nothing.
  - The new page's player takes back all that was handed over and asks for none of it again.
  - The test checks that the old player came back: with `StayedMs` at 10 s it fails there.
  - Segments still downloading at `beforeunload` (2 to 5 in these runs) are not in the hand-off,
    in any reload: the new player asks for them again.
- C-2: two tabs with the same page and video that both reload within 20 s share one key. The
  second hand-off flushes the first (`BufferStash.put`), and the first new player takes what is
  left: the same video's bytes. The other tab downloads again. Nothing crosses a container or
  a private window (both are in the key). Left as decided: with the tab in the key, a tab
  closed and opened again never gets its buffer back.

## 5. Where to look next

The owner's themes for this round, with what is known for each. Every change needs a test that
fails before it, and anything that touches loading, seeking, startup or timers an A/B run.

**Security bugs.** Where a page or a server feeds the extension: the content scripts'
messages (`MessageSenders` in `background.mjs`; the fuzz test covers the background's side, not
what the content scripts do with what the page gives them), the page transport (requests made
through the page, #669), `RequestUtils`, the MP4 and HLS parsers on hostile files (PE-7), the
mpv helper's native messaging (`native-host/`), the options import, `UrlMatchList` regexes the
user types (a catastrophic one runs on every address).

**Logic flaws.** The turns between tabs (`PlayerTurns.mjs`, `PlayerPeers.mjs`): a player that
says it wants the network and never downloads, clocks of hidden tabs, two windows. The reload
retry (`noteOpenMissed`, `reopenMissed`, `reopenOnUserPlay` in `background.mjs`): a page that
takes the player out again and again. The next-episode instructions (`continuationPage`,
`endContinuation`).

**Pipelining.** Downloads ahead start at the client's tick or a finished download, up to 1 s
after a seek (A3; left because started before the player's own request they would take its
priority). The page transport copies each chunk twice over two hops (measure first). A
`SET_HEADERS` round trip per request.

**Firefox and the extension.** The Firefox API watch (below) lists what each release changes.
Known candidates: `runtime.getVersion()` (Firefox 158) instead of reading the manifest;
MediaCapabilities' HEVC answers on Windows (fixed in 158); whether the active-tab-first order
Firefox gives one host's connections (measured: it does) can be relied on.

**The operating system.** FastStream is Firefox-only, and the one OS-specific code is Windows'
AAC channel layouts (`AacLayout.mjs`: Windows' decoder refuses some). Others are possible
(Linux's and macOS's decoders, Windows' Media Foundation and HEVC), but only where a measured
difference exists; the CI runs Windows and Linux.

**Refactors and rewrites, with what each would buy.**

- `MP4Player.refreshSampleIndex` was quadratic on fragmented files. Done on 2026-11-15 (#685):
  `RangeTimes` works out again only the ranges new samples fall in, 1.65 ms a call to 0.07-0.13
  at 2 h, and the whole list as before once it is out of order.
- `MP4Player`'s steady loop runs every 50 ms while playing (could be 250 ms at `readyState` 3).
  Its `needsInit` wait looped every millisecond for good; since 2026-11-15 only for 2 s after
  the last step forward, then every 50 ms, woken at once by `loadeddata` and the duration
  (`docs/notes/player.md`, "The polish round").
- PC-4 (one buffer written in place for a download with a `Content-Length`) was measured on
  2026-11-15 and not built: the peak stays the same, as the pieces are freed only at the next
  collection (same section).
- `SaveFile.add` copied each fragment once more than it needed. Done on 2026-11-15 (#683): a
  fragment whose buffer is its own is taken as it is.
- Startup: `sortable.mjs` (119 KB), the subtitle search (43 KB) and `gif.mjs` (14 KB) load with
  the player. Measured on 2026-11-15 in the installed extension (Firefox 160, 8 rounds, each
  import alone in a fresh extension page, so an upper bound): sortable 5-6 ms warm (7 cold), the
  subtitle search 6-7 (10 cold), gif 3-4. The whole player page loads in 37-49 ms warm (70 cold);
  the first frame comes at about 550 ms (the A/B bench). Not built: sortable and the subtitle
  search are both made at startup (`ToolManager`, `SubtitlesManager`), so loading them later
  changes what the toolbar can do in its first moment; gif alone is used only on demand, and 3-4
  ms is below what the bench can tell apart.
- The UI: the progress bar reads every fragment per fragment event (it writes the DOM only
  where something changed; about two events a fragment: looked at on 2026-11-15 and left); a
  paused video's controls are checked every 2 s. The settings sliders save once a frame while
  dragged (OP-6), not at every input event.
- The background: `deleteHeaderCache` could join the first `onHeadersReceived` listener. The
  tab state is written at every address change of every tab; skipping a write of equal state
  would save nothing there, as the address is part of it (looked at on 2026-11-15). The tab
  icon is set on every `onUpdated` of an address or a load, as Firefox resets the button on
  every new document.
- CSS: done on 2026-11-15. The transitions, animations and keyframes under the zero-motion
  override, and the selectors nothing uses, are gone (`playerA11y.test.mjs` keeps them out).

## 6. How to review

- Each reviewer gets the diff of one area at a time, the notes section that explains it, and the
  question; glm sees only what it is sent, and runs 5 to 20 minutes. Every claim is checked
  against the code before anything is changed; earlier rounds had about one real finding in
  three.
- Never run the mpv e2e specs on the owner's PC. One Firefox at a time; one e2e run at a time
  (fixed ports).
- Nothing personal in what is committed (`tools/privacy-check.mjs` runs as a hook and in CI).
- Each fix is a pull request into main with its test, CI and CodeQL green (read CodeQL after its
  JavaScript analysis has landed: `docs/notes/workflows.md`). Before the releases are turned on
  again: the checks of section 2 on main's last commit, and an A/B run against 4813fbee.

## 7. The Firefox API watch

`.github/workflows/firefox-api-watch.yml` and `tools/firefox-api-watch.mjs` (#674, in this
branch, `docs/notes/workflows.md`, "Firefox API watch"). Once a day it reads the current Firefox
release; for each new one it reads MDN's notes for developers, browser-compat-data, Bugzilla and
the add-ons blog, matches what changed against what FastStream's code uses, and opens one review
issue for the owner with a checkbox per finding, its priority, the code it concerns and what to
do. A release with nothing relevant posts nothing. A scheduled workflow runs only from main,
so it never ran before PR #679's merge; from then on it runs daily (07:40 UTC), and can be run
by hand from the Actions tab ("Firefox API watch", with `dry_run` to see what it would post).

A local dry run on 2026-11-14 for Firefox 158 to 160 (`node tools/firefox-api-watch.mjs
--dry-run --no-github --from 158 --to 160`) worked: Firefox 158, for example, gave six findings,
among them `runtime.getVersion()` and three media bugs (HEVC in MKV, MediaCapabilities).
